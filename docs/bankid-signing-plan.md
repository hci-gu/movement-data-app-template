# KontoAPI authentication and explicit consent

The backend serves one study. KontoAPI authenticates a BankID identity; it does
not sign the study document. The app records a separate, explicit consent
acceptance after authentication. Guardian pages follow the same sequence.

This replaces the direct BankID client and signature collections. Use a fresh
database; no legacy data conversion is provided. The `bankid` command group
and `/api/bankid/attempts` paths retain their names for BankID-facing operations.

## Participant sequence

1. The app creates an authentication attempt with a random ID and secret.
   Starting the same ID/secret/mode twice is idempotent. A lost start response
   does not start another upstream order automatically.
2. KontoAPI creates the order. Same-device handoff uses its auto-start token;
   another device scans an image generated by KontoAPI. QR secrets stay on the
   server. Return manually from BankID; the documented wrapper has no return-URL
   parameter.
3. The server polls status, validates the returned personal number and derives
   age and registered gender. An accepted authentication creates/finds the user
   and grants a two-hour session. It does **not** create consent.
4. An authenticated user without current consent is routed to `/consent`.
   The app fetches the current document with its session, displays the full text,
   and requires explicit acknowledgement and acceptance.
5. `POST /api/consent/accept` binds the exact current document ID/hash, user,
   authentication event, acceptance time and idempotency key. A stale document
   returns 409; the app reloads it and requires review again.
6. Tasks unlock only after current consent and any required guardian approvals.
   Returning participants with an active current acceptance go directly home.

Authentication-only sessions may read their state/current consent and accept.
Questionnaires, answers and uploads remain blocked until consent and guardian
requirements are satisfied. Password login, generic collection writes or a link
cannot substitute for the accepted authentication event in the session token.

## Guardian sequence

Participants under 18 select one or two guardians. The backend requires distinct
guardian personal numbers; a guardian must authenticate as the requested adult.
An invitation alone grants neither identity nor approval.

The browser stores an opaque attempt credential in a Secure, HttpOnly, SameSite
cookie scoped to the invitation. Status, QR and return pages verify ownership;
approval and restart POSTs also require a CSRF nonce. Participant details and
consent are shown after authentication. The explicit approval is bound to the
participant's current acceptance and the exact document/hash. Refreshing or
replaying a successful approval is idempotent.

Withdrawal, a new participant acceptance or a new consent version invalidates
old approvals. An identity mismatch cannot approve. Guardians do not receive
participant sessions.

## Persistence and evidence

| Collection | Purpose |
| --- | --- |
| `users` | Verified personal number, account token key, selected guardian count. |
| `authentications` | Terminal participant/guardian authentication outcomes and encrypted provider evidence. |
| `consent_texts` | Immutable, versioned text and SHA-256 hash; one current version. |
| `consent_acceptances` | Explicit participant acceptance linked to identity event, document, withdrawal state and encrypted evidence. |
| `guardian_requests` | Participant/slot and requested guardian identity; numeric invitation ID. |
| `guardian_approvals` | Explicit approval linked to identity event and participant acceptance, with encrypted evidence. |
| `questionnaires`, `questions`, `questionOptions`, `answers`, `dataUploads` | Existing questionnaire and upload behavior. |

Evidence is authenticated encryption under the study keyring, with collection
and record ID as associated data. Authentication evidence contains the provider
result/order reference; consent evidence contains the full document and method
`inAppAcceptance` (guardian approval has its own evidence context). These are
application records of consent after identity verification, **not BankID text
signatures**. Names returned by KontoAPI are not used to establish authorization.

Receipts display the accepted document and acceptance date. Withdrawal marks
all unwithdrawn acceptances and rotates the user's token key, revoking sessions.
Rejoining requires fresh authentication and acceptance; old guardian approvals
cannot be reused. Evidence remains encrypted for audit; withdrawal is not deletion.

## Provider and attempt lifecycle

The provider uses ADFS client credentials with cached bearer tokens and
`x-api-key`. Endpoints from the supplied Word example:

- GET `/api/Bankid/GetQrAndMobileAuthRef/{ip}`
- POST `/api/Bankid/GetQrImage`, with the complete returned QR object
- POST `/api/Bankid/GetAuthStatus?getName=true`, with `{orderRef}`

Empty status is pending. A complete result must contain the documented
`personalNumber:givenName:surname`; malformed/unknown results fail closed.
QR frames must be bounded PNG data URLs. No arbitrary provider URL is fetched.
The real response format still needs verification on the GU VPN.

Bearer expiry uses OAuth duration semantics. Collect/QR may refresh once on 401;
order creation is never automatically retried. Transport timeouts, bounded
responses and sanitized errors keep upstream failure details and credentials
out of participant responses. Only configured proxy CIDRs can supply client IPs.

Attempts live in process memory, bounded to 1,024. Run one replica. Local order
lifetime is three minutes, completed results remain retrievable for ten minutes,
and server polling runs every two seconds (with backoff for 429/5xx). Restarting
the server interrupts pending attempts. Persisted records survive.

The wrapper documents no cancel endpoint: **Stop this request** stops local
polling and prevents that attempt from granting a session, but cannot cancel
the upstream BankID order. The QR image is cached briefly; Flutter/browser
polling retrieves fresh frames while pending. Optional existing return links
only trigger verification of an owned attempt; they never grant access.

## Scope and validation

The source is the supplied `Kodexempel för BankID inloggning mot kontoapi.docx`.
The user approved discarding all prior data and the authentication-then-consent
sequence. The template's shared document and under-18 guardian threshold remain.
The scoliosis material in `context/` describes study-specific consent audiences;
adapting those texts/thresholds, branding and questionnaires is separate work.
This implementation does not establish that an in-app acceptance meets those
study requirements.

See [setup/testing](bankid-testing.md), [manual review](manual-review.md), and
the generated report for automated results. Live successful identity responses,
QR refresh, same-device handoff and guardian browser completion require VPN and
test BankID/device interaction before participant use.
